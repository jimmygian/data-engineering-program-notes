
Dbt provides an easy way to create new tables by wrapping each SQL statement with another SQL statement that will create the tables under the new schema. 

Dbt also **helps you document and validate your data within your database or data warehouse.** 

Let's first install dbt and set up the environment. Dbt provides two types of environments, 
- **dbt core**:
	- an open source command line tool that you can install locally in your own environment
	- and communicate with your databases through adapters. 
- **dbt Cloud**: 
	- which runs dbt core **in a hosted environment** with a **browser based interface**. 


Here in the terminal, I'll create a new virtual environment and then I'll activate dbt-core. 

```shell
python -m venv dbt-env
dbt-env/bin/activate

python -m pip install dbt-core dbt-postgres
```
	dbt-core is the environmnet we choose to run
	dbt-postgres is the adapter we want to connect to dbt-core

Depending on the type of database or data warehouse you're using, you can choose other adapters. You can find the list of adapters in the **[dbt documentation](https://docs.getdbt.com/docs/build/documentation)**. 

After dbt-core and dbt-postgres have been installed, I'll create the dbt project folder that will contain the files used to define the new tables. I'll run the `dbt init `command, specifying the name of the project to be `dbt_tutorial`. 

```shell
dbt init dbt_tutorial
```

Then dbt will ask you to specify the type of database. Since I've only installed dbt-postgres, I just have one option, so I'll type one. Then dbt will ask you to enter the database information to automatically create the file that contains the connection details to the database. 

For now, I'll stop this process by typing `CTRL+C`. I'll show you how to manually create this file later. 

After you run `dbt init`, a folder labeled `dbt_tutorial` will be created in your working directory. 
	
Here are the folders and files created in the dbt tutorial project folder.

### `model/`
The `model` sub folder is the main directory where you'll spend most of your time. In this directory, **for each table** you want to create in your star schema, you'll create a`.SQL `file that contains an SQL statement that defines the corresponding table. 

In the same directory, you can add a `.yaml` file to define some model configurations and some other testing and documentation information.

![[Screenshot 2026-01-31 at 12.31.49.png]]

When you initialize your project, some example files will also be generated under the models directory. Feel free to take a look at them, but we won't use them, so I'll delete them when I create the files for our star schema. 

### `analyses/`
You can use the `analyses` sub folder to include any SQL statements that **are not part of your models directory** and that could be a part of **your own exploration**. When you run `dbt`, only the SQL statements that are in the `models` sub folder will be executed. 
![[Screenshot 2026-01-31 at 12.34.52.png]]

### `macros/`
In the `macros` sub folder, you can store **pieces of SQL code that you want to reuse multiple times** in your `models` directory. 
![[Screenshot 2026-01-31 at 12.35.20.png]]

### `seed/`
In the `seed` sub folder, you can have some **CSV files** that you want to load into your data warehouse or database using **dbt**.
![[Screenshot 2026-01-31 at 12.35.37.png]]

### `snapshots/`
In the snapshots sub folder, you can ***record the changes in your tables over time***. 

### `test`
Finally, in the `test` sub folder, you can create SQL statements to perform some specific tests on your data.

### `dbt_project.yaml`

![[Screenshot 2026-01-31 at 12.36.03.png]]

In addition to these sub folders, there's also this `dbt_project.yaml` file that's also automatically generated by `dbt init` command. This is an important file that contains the **configurations of your project**, so let's take a look at the file. 

```yaml

# Name your project! Project names should contain only lowercase characters
# and underscores. A good package name should reflect your organization's
# name or the intended use of these models
name: 'dbt_tutorial'
version: '1.0.0'

# This setting configures which "profile" dbt uses for this project.
profile: 'dbt_tutorial'

# These configurations specify where dbt should look for different types of files.
# The `model-paths` config, for example, states that models in this project can be
# found in the "models/" directory. You probably won't need to change these!
model-paths: ["models"]
analysis-paths: ["analyses"]
test-paths: ["tests"]
seed-paths: ["seeds"]
macro-paths: ["macros"]
snapshot-paths: ["snapshots"]

clean-targets:         # directories to be removed by `dbt clean`
  - "target"
  - "dbt_packages"


# Configuring models
# Full documentation: https://docs.getdbt.com/docs/configuring-models

# In this example config, we tell dbt to build all models in the example/
# directory as views. These settings can be overridden in the individual model
# files using the `{{ config(...) }}` macro.
models:
  dbt_tutorial:
    # Config indicated by + and applies to all files under models/example/
    example:
      +materialized: view

```
##### name / version config
In this file you specify the **name** and **version** of your dbt project. 

```yaml
# Name your project! Project names should contain only lowercase characters
# and underscores. A good package name should reflect your organization's
# name or the intended use of these models
name: 'dbt_tutorial'
version: '1.0.0'
...
```
##### profile configs
Next, you select the **profile** for your project. The **profile** should contain the *details for connecting to the database*, and you need to define the profile within a yaml file called `profiles.yaml`. Here, dbt automatically labeled profile with the project name. I'll leave it as it is, but you can definitely choose another name for the profile. 

```yaml
...
# This setting configures which "profile" dbt uses for this project.
profile: 'dbt_tutorial'
...
```

##### dir configs
Next, you'll define the **directory** configurations that tells dbt where to find the sub folders of your dbt project. 

```yaml
...
# These configurations specify where dbt should look for different types of files.
# The `model-paths` config, for example, states that models in this project can be
# found in the "models/" directory. You probably won't need to change these!
model-paths: ["models"]
analysis-paths: ["analyses"]
test-paths: ["tests"]
seed-paths: ["seeds"]
macro-paths: ["macros"]
snapshot-paths: ["snapshots"]

clean-targets:         # directories to be removed by `dbt clean`
  - "target"
  - "dbt_packages"
...
```

- *With `clean-targets`, you can specify the directories to be removed when you run `dbt clean`.* 
	- The `target` directory contains the compiled SQL files of your models that will be created after you run dbt, 
	- and the `dbt_packages` is a directory that you can create to store third party packages if your project depends on them. 

##### default cionfigs
Finally you can specify the **default** **configurations** for your `models`. This includes whether you want to create the models as **tables** or **views** in your database. 

```yaml
...
# Configuring models
# Full documentation: https://docs.getdbt.com/docs/configuring-models

# In this example config, we tell dbt to build all models in the example/
# directory as views. These settings can be overridden in the individual model
# files using the `{{ config(...) }}` macro.
models:
  dbt_tutorial:
    # Config indicated by + and applies to all files under models/example/
    example:
      +materialized: view

...
```

>	Views mean that you only save the SQL statements without creating the actual tables. 
>	
>	You can specify this information using the materialized key. You have defined multiple sub directories inside of the models directory, you can organize the model configured by the sub directories. 
>	
>	In this example, we're telling dbt to create *all models defined under the* `example` sub directory as **views**. Later, I'll delete this configuration and replace it with the configurations for the actual tables of the star schema. 


#### Creating the `profiles.yaml` 

Now, let's create the `profiles.yaml` file to specify the connection to my local postgres database. Inside the dbt tutorial project, I'll create profiles.Yaml. ![[Screenshot 2026-01-31 at 12.56.14.png]]

>	*You can specify in this file, **more than one profile** and each can correspond to one data warehouse.* 

Here, I'll create one profile labeled as `dbt_tutorial`. Make sure that the name of the project matches the names you specify in the project configuration file. 

```yaml
dbt_tutorial:
```

The profile can consist of multiple targets where you can specify different connection details under each category. 

For example, you might need to create two targets, 
- one for development 
- and another for production. 

You list these targets under the `outputs` key.

```yaml
dbt_tutorial:
  outputs:
    dev:
      type: postgres
      host: localhost
      user: ostgres
      password: admin_pwd
      port: 5433
      dbname: postgres
      ...
```


I'll specify one target that I'll call `dev`. To populate this target, I'll specify the database `type` which is `postgres` in this case, then I will specify the database credentials. 

For a postgres target, I'll specify the `hosts`, `user` name, `password`, `port` number, and `dbname`. 

>	NOTE: In the dbt documentation, you can find a sample profile **for each possible target type**. 


Finally, I'll specify that this dbt project will run on one thread, and that the default schema is a star schema. 

```yaml
dbt_tutorial:
  outputs:
    dev:
      type: postgres
      host: localhost
      user: ostgres
      password: admin_pwd
      port: 5433
      dbname: postgres
      threads: 1
      schema: star_schema
```

To wrap up the dbt_tutorial profile, I need to specify the **default** target, which is `dev`, because that's the only target I have right now. 

```yaml
dbt_tutorial:
  outputs:
    dev:
      type: postgres
      host: localhost
      user: ostgres
      password: admin_pwd
      port: 5433
      dbname: postgres
      threads: 1
      schema: star_schema
    target: dev
```


To verify the connection to the database, I'll go to the terminal and I'll make sure that I'm in the project directory, and I'll type `dbt debug`. 

```shell
cd dbt_tutorial
dbt debug
```

If there's no issue with the credentials, you should see that the connection is okay.

## `models` creation

Inside the `modles` subdirecrory we can remove the `example/` folder and create a new one called `star_schema_models`. In there, we can start creating `.sql` files. Dbt will use the name of these sql files to create the tables.

```shell
mkdir models/star_schema_models
touch models/star_schema_models/dim_stores.sql
```

In this file i'll type in the query for the dim_stores table:

```sql
select MD5(store_id) as store_key,
    store_id,
    store_name,
    store_city,
    store_zipcode,
from staging.stores;
```

>	 `staging.` is the database we created in our postgres.

In the same subdirectory, you can also create a YAML file to configure your schema for documentation and testing purposes. Here, I'll create a `schema.yml` file. 

To document the information about the model, I have to specify the key models. Then I'll specify the name of the table and then the name of the columns. You can add a description about the table. 

```yml
version: 1
models:
    - name: dim_stores
    - name: store_id
    - name: store_name
    - name: store_city
    - name: store_zipcode
```


For each column, you can also add a description and specify any of the **generic tests** provided by DBT. 

```yml
version: 1
models:
  - name: dim_stores
    description: Stores dimension table
    columns:
    - name: store_key
      descriptionn: The primary key for the table
      data_tests:
      - unique
      - not_null
    - name: store_id
    - name: store_name
    - name: store_city
    - name: store_zipcode
```
>	Here, for the `store_key` column, I'll add a `description`, saying that the store key is the primary key for the dim stores table. I'll also add **two tests** to verify that the values of store key are **unique** and **not null.** 

There are two other generic tests: 
- You can use ***accepted_values*** to check if a column takes in values from a list of accepted values 
- and ***relationships*** to verify how two columns are related to each other. 
- You can also create **your own custom tests**. 


I'll create the SQL files for each of the `dim_items`, `dim_date` and `fact_orders` tables, and then type the corresponding SQL query inside each file. 

In the `schema.yml` file, I'll add a description for each table, and for each primary key, I'll add a description in the same tests. 

>	*NOTE: Make sure to pay attention to the indentation when working in a YAML file.*

### `dbt_project.yml`

Before we run DBT to create the tables, let's update the default configuration for the models in the `dbt_project.yml` file. 



- Here, I'll remove the configuration for the example and replace it with the name of the subdirectory we created under the models directory, which is `star_schema_models/`. 
- Then I'll specify `table` as a value for the materialized key. This ensures that all the tables are actually created in the database. 
- We can also specify the `+schema` key. For example, if I specify `analytics` for the schema, the schema value will be appended to the default schema name in the `profiles.yml` file. This way, the tables will be stored under `star_schema_analytics`.![[Screenshot 2026-01-31 at 15.15.25.png]]
  In this case though, we won't include this, to ensure that the tables will be created under the schema `star_schema`.
 
 >	*Note that you can also specify these configurations under the `models/` directory, which will override the default configuration of the  `dbt_project.yml` file.* 


### Running dbt
 Now that we've defined the tables for the star schema, let's run DBT to create the tables. In the terminal, I'll make sure that I'm in the project folder, and then run the `dbt run` command. 
 
 If you have more than one subdirectory under the models directory, you can select which models you want to execute using the `-S` or `--select` options and then specify the name of the subdirectory. 
 
 For example, I can execute star schema models by typing `dbt run -S star_schema_models`. 
 But here, since I only have one subdirectory, I can remove this option. 

To verify that all tables have been created from the terminal, you can establish a connection to the database server and check whether the database and tables have been created.

DBT has other features, which you'll use in this lab. For example, instead of using the `MD5` hash function to generate surrogate keys, you'll use a utility function to create your own surrogate keys. You'll also use a DBT date package to generate a complete date dimension table that has all of these fields.
