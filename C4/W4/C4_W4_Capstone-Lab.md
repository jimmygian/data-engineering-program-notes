In this section, I'll walk you through the business problem and the architecture of the proposed solution and give you an overview of the tasks in Part 1 of the lab. 

Assume you work as a data engineer at a company called ***DEFtunes*** that offers subscription-based music streaming services. 

The company *recently added a new feature*, allowing its clients to **purchase** and **download** music. The **data analytics team** is interested in *analyzing the data generated by this new feature*, so your tasked with building a data pipeline that makes the purchase data available to the data analysts. 

![[Screenshot 2026-02-17 at 21.07.36.png]]

From speaking with them, you learn that they're interested in: 
- analyzing the purchase data with respect to the **song** and **artist** features, 
- how these purchases are **evolving over time**, 
- and how they're affected by the **user's personal information such as location**. 

This analysis will help the company track how the new service is performing. The purchase data is available through an **API** that the **software engineering** team has set up for the new service. 

The software engineering team share with you a link to their *API documentation*, where you have two main endpoints, sessions and users. 
![[Screenshot 2026-02-17 at 21.08.55.png]]

- The ***sessions*** endpoint allows you to access the information for the transactional sessions that occurred over a period of time. 
	The response to this request contains information about each session, such as the user ID associated with the session, and the list of song items purchased by the user during that session. For each purchase item, you can see information about the song and the artist, the price of the song, and the like status of the song. 

- The users endpoint allows you to access information about the users who had sessions over a period of time. 
	The response to the GET request contains some information for each user, such as their first and last names, their location and time zone, and the date they subscribed to the app. 

You also have access to a ***database*** that contains information about all the songs users can purchase. It's a **PostgreS Sequel database** that consists of one table called *Songs* that's defined under the DEFtunes Schema. The table contains the track ID, title release album, some artist information, and the year of the song was released. 

![[Screenshot 2026-02-17 at 21.10.53.png]]


Your job is to 
- ingest, 
- combine, and 
- model this data 
so that the data analysts can efficiently query the data they need for their analysis. 
- Also, you're required to **store** the historical raw data, while updating the model data daily.

The company also has **two storage options**, a *data lake bucket* (**S3**) and a ***Redshift cluster*** that you can ***use to build the data pipeline***.

##### Modeling the Data
To get started, you need to first ***decide on how you want to model the data***, which will then inform how you'll process the raw data. 

Throughout this course, you learned that the **star schema** can be useful for analytics. What do you think the fact and dimension tables should represent in your star schema? Since the data analysts are interested in analyzing the ***"song purchases"***, the **atomic grain** for the **fact** table should correspond to a **single item purchased within a session**, and since they're interested in how the purchases vary with respect to the user, time, song and artist features, we could create these **four dimension tables** to provide the additional context. Now, for the fact table, since each row should represent an item purchased within a session, we need to have the session ID and the song ID to uniquely identify each row. From these two columns, we can create a ***surrogate key*** for the table, which I'll call fact key. We also need to have four foreign keys to connect the fact table to the four dimension tables, song key, user key, artist key, and session start time. Finally, we need to include the quantitative measures, which include the price liked and liked since. For simplicity, let's assume that all prices are in US dollars or USD. If the prices were represented in different currencies, you could convert them all to the same currency in the transformation or serving layers. 
Or you might create two columns in the fact table, one containing the prices in their original currency and another containing the converted prices. In any case, you should provide clear documentation to your stakeholders so that they know how to properly interpret the data. 
![[Screenshot 2026-02-17 at 21.16.45.png]]


You can 
- ***model the data using the star schema model*** and 
- store the data in the ***data warehouse***  (Redshift) for the data analysts to efficiently execute their analytical queries, 

but before that, you need to 
- **extract the raw data from the data sources**, 
- then **combine and store it before sending what is needed to the data warehouse**. 

You can bring the historical raw data into the data lake bucket to save on storage cost, then transform and enrich the data before storing it in another zone in the same data lake bucket. 

Then finally, you can model the data in the data warehouse.

#### Architecture Diagram of Solution
Here's the architecture diagram of the proposed solution you'll implement in the lab. 

#### Data Ingestion

- You will first bring the raw data from the API and the database into the landing zone of the data lake bucket by extracting the data using ***AWS glue ETL jobs*** defined in ***Terraform***. 
	- You'll define **two glue jobs** to *extract data from the users and sessions API endpoints* and another **glue job** to *extract the song data from the Postgres database*. 
		- In the first two jobs, you'll store the users and sessions data as JSON files using two S3 paths. These paths end with a **timestamp** to indicate when the data was ingested. 
		- In the third job that extracts data from the database, you'll store the song table as a CSV file using another S3 path. 

![[Screenshot 2026-02-17 at 21.20.00.png]]


Then you'll **process the raw datasets** by enriching each one with some **lineage metadata** using two **glue ETL jobs** defined in **Terraform**. 
![[Screenshot 2026-02-17 at 21.22.54.png]]


#### Transforming the Data

- In the transform JSON job, you'll 
	- extract the user JSON file into a data frame. 
	- then process the user location field by creating columns for latitude, longitude, place name, country code, and time zone. 
	- You will also have a column that represents when the data was ingested into the landing zone and another column that represents the processing time. ![[Screenshot 2026-02-17 at 21.24.19.png]]

- In the same transform JSON job, you will also extract the Sessions JSON file into a Spark data frame. 
	- You will process the Sessions JSON file by **extracting each item from the session items array into a row in the data frame.** 
	- You will also add a column that represents when the data was ingested into the landing zone and another column that represents the processing time. 
	  ![[Screenshot 2026-02-17 at 21.24.55.png]]

You'll store both tables as ***iceberg tables*** using these paths. 

![[Screenshot 2026-02-17 at 21.25.40.png]]


With the transform songs JSON job, you'll 
- extract the CSV file into a data frame, 
- perform schema enforcement, and 
- add two columns that represent when the data was ingested and the database name. 
![[Screenshot 2026-02-17 at 21.27.04.png]]

You'll store the data in an iceberg format using this path. 
![[Screenshot 2026-02-17 at 21.27.19.png]]


#### DB Catalog "Transform DB"
You'll also create a database catalog called transform DB. ![[Screenshot 2026-02-17 at 21.29.37.png]]

Then for **each of the three tables** you created an iceberg format, you'll create **associated tables in the database catalog**, and finally, you'll **model the data using the star schema model** and **store the model data in the data warehouse**, which will act as a **serving zone in your data pipeline**. 

Here, you'll use the Red Shift spectrum feature which allows you to query the process data from the transformation zone of the data lake bucket without first having to load the process tables into the Red Shift cluster. 
![[Screenshot 2026-02-17 at 21.30.14.png]]


In Terraform, you'll define this Red Shift provider, which allows you to interact with and manage the Red Shift cluster. To use this provider, you need to specify the credentials of your Red shift cluster. Then you'll use the Red Shift schema resource to create two schemas. An internal schema under which you'll store the data modeled using the star schema and an external schema that references the transform DB catalog database in the glue data catalog. Here you'll need to specify an IM role to allow Red Shift spectrum to access the S3 bucket. This role is already created and provided to you. 

After you run Terraform, you'll be able to query the data from the S3 bucket and then model your data using DBT. Here are the main resources of the proposed architecture you'll implement in the lab. 

They're organized similar to the medallion architecture, where the landing zone represents the bronze zone, the transformation zone represents a silver zone, and the serving zone represents the gold zone.
